# 公开内容请求缓存

## 范围与约定

用户2026-11-18确认：按下表启用内存短缓存和并发请求合并。手动刷新绕过已有结果，保留真实获取时间和失败提示，专项验证行情及价格警报未接入；权限不调整，不提交代码。

| 组件 | 来源标识 | 成功结果有效期 |
| --- | --- | --- |
| 热榜（五个可切换来源） | bilibili、douyin、tou-tiao、weibo、zhihu | 30秒 |
| 财联社电报 | cls-telegraph | 10秒 |
| 日历、大号日历的在线黄历/节假日 | itime-calendar | 1小时，跨日或UTC偏移变化失效 |
| B站推荐 | bilibili-rcmd | 不保存结果，只合并同参数在途请求 |

缓存时长不改变组件原刷新周期，不新增后台轮询或向其他视图推送更新。界面可能本轮得到缓存、下次刷新才变化；手动操作可以重新取数。

股票、指数、币价、黄金、贵金属、汇率、价格警报、天气、AI及登录内容均不进入此缓存。

## 实现与兼容

- `content_cache.rs`只被公开内容网关调用，通用HTTP、行情服务及警报引擎不接入。缓存不写入SQLite或磁盘，进程退出后清空。
- 新版11款组件显式传入`cache:true`，已有手动刷新/重试入口传入`forceRefresh:true`。旧包未传缓存标志时仍走原直接读取路径；日历的新包遇到旧宿主明确拒绝新增元数据时兼容原接口，真实网络失败不自动降级或重试。
- 按来源、语义参数、有效网络设置隔离；对象字段顺序不影响命中。黄历额外包含本地日期及UTC偏移，避免跨日/时区复用。
- 手动刷新先移除已有结果，可以共用正在进行的新请求。HTTP失败、来源错误状态、无效JSON/数据结构均不缓存，不用旧成功结果代替失败。
- 每份响应保持第一次真实取数时的`source`、`fetchedAt`和内容。缓存命中不重写时间；等待返回后仍检查当前会话、能力和网络配置，不向已失效页面交付结果。
- 最多32份成功结果、8MiB序列化内容、32个不同参数的在途合并记录；超过成功结果预算时淘汰最早记录，合并记录满时继续直接取数，不新增业务限流。实际网络读取沿用原8秒超时、2MiB响应上限和禁止重定向规则。
- 不修改实例标识、设置和存储结构。公开内容缓存按来源和参数区分。
