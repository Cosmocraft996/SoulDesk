# 桌面组件 — 技术实施方案与交付计划

> 版本：v1.4｜修订日期：2026-11-13｜状态：正式桌面改造已实施，0.4.0 本地候选验收中；证据见11  
> 产品目标与验收以 [01-需求文档-PRD.md](01-需求文档-PRD.md) 为准；源码版本、许可、用户确认和既有测试见 [03-参考项目源码审计与需求确认.md](03-参考项目源码审计与需求确认.md)。0.4.0 已实施正式展示协调器，隔离验证、视觉和普通安装结果分别记录于11。

## 1. 技术决策与验证门槛

### 1.1 推荐路线

现有工程采用 Tauri 2 + Rust + React/TypeScript + Vite：Rust 核心负责展示协调、持久数据、共享行情和警报；网页视图负责交互与展示。先保留现有工程与后台，不仅因展现形式偏差就替换技术栈；是否满足独立桌面组件目标，必须补做宿主专项验证。

产品主次已确认：独立桌面组件为主，快捷键和侧边组件面板为辅，管理窗口负责添加与设置。用户已认可草图与中性深色宿主、独立多彩组件的方向。旧方案“工作台中嵌入、少数实例移出浮窗”的默认路径停止沿用；第3节交互已按用户最新授权进入正式实施，证据见11。

[Tauri 官方进程模型](https://v2.tauri.app/concept/process-model/)支持核心进程管理窗口、全局状态和网页视图的职责划分。它是架构依据，不是本项目的实机通过证明。

| 决策 | 理由 | 验证与退出条件 |
|---|---|---|
| 保留 Tauri 为现有候选宿主 | 复用已有后台与加载能力，先验证纠偏后的桌面目标 | 补证独立组件展示、基础桌面层级、Win+D、恢复及管理界面分离；旧 G0 不替代此专项 |
| Rust 集中运行关键服务 | 监控不依赖隐藏页面计时器，多个视图共享业务 | 销毁视图后后台测试事件仍触发；渲染错误不会停止规则 |
| 普通组件采用独立静态页面包 | 可安装 HTML/CSS/JS 产物，不依赖源代码动态 import | 从主程序外部导入包，在生产安装版成功加载、卸载及重建 |
| 复用组件包与宿主消息契约，调整展示宿主 | 现有 iframe 容器可作为复用候选；桌面组件与辅助面板不另造业务后台 | 桌面承载方式须经专项决定；验证键鼠、缩放、布局及常驻和隐藏时的资源成本 |
| 关键持久状态集中于 SQLite | 规则状态与触发历史可在同一事务保存 | 保存失败、进程中断、迁移失败及备份恢复检查 |
| 首版仅手动安装升级 | 满足个人使用，避免先建设更新服务 | 覆盖重复安装、旧数据保留和失败恢复 |

G0 若发现阻碍核心目标的问题，先记录最小复现和替代代价。组件容器问题先评估单一独立网页视图方案；宿主层关键能力无法满足时再比较 Electron 或 WPF/WebView2。备选由 Codex 给出证据和推荐，只有影响宏观范围或成本时才交用户决定。不同时实现多条宿主路线。

原 v1.1 的 G0 已通过：普通桌面安装版完整探针完成 14 项程序检查，启动上下文无外部包身份，用户确认通知及声音正常。证据见 [04-G0实施与验证记录.md](04-G0实施与验证记录.md)；只复用其实际覆盖的能力；桌面最小专项已在09通过，正式入口证据见11。原有缩放、副屏和不同 Windows 设备缺口继续保留。

### 1.3 本轮路线比较

| 路线 | 收益与成本 | 本轮判断 |
|---|---|---|
| 保留现有后台与组件包，补 Windows 桌面展示适配 | 保留业务和持久化证据，修改集中在展示归属、会话和界面；桌面附着仍有系统兼容风险 | Codex 推荐；先做最小专项，不直接承诺成功 |
| 仅把旧浮窗取消边框并设为底层 | 变更少，但不能证明 Win+D、桌面图标、缩放及桌面宿主重建符合目标 | 只能作为验证中的对照，不能当成目标交付 |
| 立即更换整个宿主或重写后台 | 需要重建大量已有集成与验证，当前没有证据证明必须如此 | 当前不采用；若桌面专项失败，再报告具体替代代价和范围 |

以上是 Codex 的技术建议，不写成用户已指定技术路线；关键能力以锁定版本源码、官方资料和本项目实测分别标注。

### 1.2 工具链与依赖纪律

- 使用一个仓库、一个桌面宿主，前端沿用现有 pnpm 工具。G0 锁定通过验证的具体版本，将依赖锁文件纳入工程；不以浮动 latest 作为构建基线。
- 初始依赖限于宿主、React/Vite、网络、精确十进制、SQLite、配置校验及必要的官方桌面插件。图表按后续需求加入，不同时引入多套 UI、图表和全局状态框架。
- 界面先用 CSS 变量和少量统一组件；全局业务状态由核心进程持有。普通页面交互使用 React 本地状态。
- 网络客户端候选为 reqwest 与 tokio-tungstenite；G0 先验证 REST/WS 的 HTTP、SOCKS5 与取消连接路径，再锁定适配实现，不能假设 WS 自动跟随 HTTP 或系统代理。
- 关键数据用 SQLite；JSON 用于组件清单、导出和诊断，不再另存一套会与数据库冲突的警报状态。
- 2026-11-12 已经用户明确授权在本目录初始化独立 Git 仓库，初始分支为 main；项目规范见根目录 AGENTS.md。后续不重复初始化，未经明确要求不提交或推送。
- 安装或升级依赖前检查适用的 AGENTS.md、README、依赖和配置；优先复用已有环境，不修改全局 PATH、默认运行时或全局包管理配置。系统级构建工具安装单独遵循授权边界。

## 2. 模块职责与数据所有权

| 模块 | 拥有的状态与职责 | 不承担的工作 |
|---|---|---|
| 展示协调器 | 独立桌面组件、辅助面板与管理界面的场景、显隐、层级和显示器恢复 | 不判断行情或警报，不以管理窗口生命周期决定桌面组件生命周期 |
| 组件管理器 | 包版本、兼容性、实例、能力和视图会话 | 不运行任意后台脚本 |
| 宿主接口网关 | 请求校验、会话身份、能力限制、订阅释放 | 不接受组件任意指定其他实例身份 |
| 行情服务 | 合约目录、订阅集合、源连接、行情质量和快照 | 不以组件是否可见决定有效规则的订阅 |
| 警报服务 | 按规则顺序判断、冷却、待补提醒、事件去重 | 不依赖 React 刷新周期 |
| 存储与递送 | SQLite 事务、备份、迁移、历史和通知结果 | 不把通知调用成功当作用户必然看见 |
| 视图容器与组件页面 | 布局、设置、状态展示及用户操作 | 不保存唯一的业务状态，不常驻连接币安 |

事件路径：

```text
交易所数据 → 校验/排序/去重 → 行情服务 → 警报顺序处理 → SQLite 提交事件与规则状态
                                  └→ 显示快照节流           └→ 通知与声音递送
组件页面 ← 宿主消息桥 ← 宿主接口网关 ← 已提交状态/行情快照
```

同一行情键的警报判断保持输入顺序。数据库操作不在界面线程执行，也不在持有共享行情锁时调用系统通知。界面快照可以合并，警报输入不能静默合并或丢弃。

组件实例配置独立；行情连接和警报规则是宿主业务对象。多个警报管理视图可以查看同一规则，不能因复制一个视图就复制出第二条规则。

## 3. 桌面展示与后台生命周期

### 3.1 状态与操作

以下为本次正式实施采用的交互约定，实施和真实证据见11。桌面组件、辅助面板、管理界面和后台分别管理生命周期；全局显隐、面板收起、组件层级和静音状态分开记录。

| 用户操作/事件 | 统一处理 |
|---|---|
| 添加一个组件实例 | 目标为直接在桌面展示，无需先添加到工作台再移出；组件库展示本身不创建实例 |
| 登录或手动启动 | 恢复上次可见的桌面组件、位置和层级；不抢焦点；辅助面板和管理界面关闭。新安装无实例时仅托盘运行，不自动创建组件 |
| 使用全局快捷键 | 默认 Ctrl+Alt+Space，仅开关辅助面板；不改变桌面组件或打开管理窗口。处于“隐藏全部”时，显式快捷键解除该状态、恢复原桌面场景并展开面板 |
| 鼠标进入侧边入口 | 展开辅助组件面板；不改变独立桌面组件的层级或配置 |
| 双击桌面空白处 | 默认启用且可关闭；核验真实Shell窗口及可访问性角色，排除图标、任务栏、组件和其他应用。显式打开保持展开，再次双击切换；隐藏全部期间不解除全局隐藏 |
| 收起面板或鼠标离开 | 鼠标悬停打开后，移出立即开始收起；快捷键和双击打开后保持展开。所属菜单、详情、拖动、缩放或输入期间暂缓，操作结束后重新核验鼠标位置；桌面组件保留 |
| 打开或关闭管理界面 | 仅影响添加与设置界面，独立桌面组件和后台继续运行 |
| 点击组件菜单中的“隐藏”或系统关闭组件视图 | 保存其展示归属和位置，仅隐藏该实例；管理界面的已添加列表可恢复，不自动移回面板，不暂停有效警报 |
| 默认桌面组件与普通应用重叠 | 普通应用覆盖组件；显示桌面（Win+D）时组件仍可见，恢复普通应用后恢复覆盖关系；组件不出现在任务栏和 Alt+Tab 中 |
| 用户选择“置顶显示” | 仅该桌面组件进入普通应用上方，不主动夺取焦点；取消置顶回到桌面层。系统安全桌面、其他应用的强制全屏不作置顶保证 |
| 移入面板或放回桌面 | 同一实例只占一个主展示位置，保持配置、自选和桌面几何；移入时显式展开面板，放回时恢复原可达位置；面板内按保存顺序排列 |
| 拖动与调整尺寸 | 标题空白区域拖动，边缘或角调整尺寸；按钮和输入区不触发拖动；尊重组件声明的最小尺寸。具体命中区域由实现细化，不新增布局编辑器 |
| 托盘“隐藏全部”与“恢复组件” | 隐藏所有组件、面板、管理界面和侧边入口，并保留恢复场景；鼠标不解除隐藏。恢复时按原实例显隐恢复桌面组件、重开侧边入口，面板及管理界面保持关闭 |
| 删除/停用一个组件实例 | 释放该实例的数据消费者与视图会话；宿主警报规则单独保留，需在警报管理中暂停或删除 |
| 显示器移除或工作区改变 | 校正独立组件到现有显示器可用工作区，保留可找回的尺寸和位置 |
| Windows 桌面宿主重建 | 重新核对并恢复桌面附着；失败时保留配置、后台和可恢复错误，不暗中改成普通浮窗或置顶来假装通过 |
| 托盘明确退出 | 停止新请求，提交待保存状态，取消连接和任务，完成退出 |

“隐藏全部”状态需保存，重启后继续保持隐藏；只有托盘“恢复组件”或显式快捷键解除。该状态下仍可从托盘打开管理界面修改配置，管理界面先提供“恢复组件显示”入口，单实例显示和新增展示需先显式恢复；不因管理界面打开或网络恢复自动解除。组件自身已隐藏的状态与全局临时隐藏分开，恢复场景不包含这些已隐藏实例。

默认目标是桌面组件模式，置顶由用户选择；具体桌面附着技术由专项验证决定。基础桌面层级和 Win+D 行为属于首版验证门槛，复杂全屏及虚拟桌面组合再按需要扩展。桌面图标、任务栏及组件外区域不得被透明大窗口拦截；不使用全屏透明画布作为首版默认承载。

所有展示动作经过同一协调器。延迟收起、鼠标展开等异步回调检查当前显隐代次，防止旧回调在“隐藏全部”之后重新显示组件或面板。

组件几何统一使用逻辑尺寸记录；转换到物理坐标时使用目标显示器的当前缩放，不直接沿用旧缩放值定位。使用系统工作区排除任务栏，恢复时校验尺寸、显示器和可达区域。保留独立拖动、边缘调整和按需操作菜单，不沿用管理窗口内前移、后移作为桌面布局方案。

### 3.2 生命周期所有者

- 核心进程生命周期不随视图数量结束；托盘常驻时拦截关闭最后窗口引发的默认退出，只放行明确退出路径。G0 必须验证全部视图销毁后核心仍工作。
- 视图卸载：释放该会话的监听、计时器和临时数据引用。
- 实例仍启用但窗口隐藏：持久自选和后台规则继续运行；暂停不必要的绘图。
- 规则拥有独立消费者标识；取消一个视图不会取消规则或其他视图的行情。
- 同一实例改变展示位置时保持 instanceId 和配置，桌面与面板主展示会话互斥；先让旧会话失效并释放临时监听，再切换新会话，失败恢复原归属。独立添加同一种组件会创建新实例，不复用另一实例的配置。
- 规则编辑和历史按需打开受宿主管理的详情界面，属于辅助会话，不是第二份主展示；按实例及角色校验权限，规则仍归核心后台，不复制规则、不自动增加行情流订阅。
- 面板收起或组件隐藏时卸载其展示 iframe，释放会话、展示轮询和临时监听；后台有效规则及持久自选消费者继续运行。恢复时取新快照；普通应用遮挡不自动当作隐藏，也不在首版新增复杂遮挡检测。
- 监听、连接和定时任务必须可枚举计数，供重复开关窗口后的泄漏检查使用。

### 3.3 外观与业务入口

沿用用户认可的桌面草图方向：组件呈现自身内容，宿主不常驻展示品牌栏、实例编号或开发指标；管理窗口负责组件库、已添加实例及设置。宿主、面板和管理界面采用中性深色；组件可独立采用多彩主题，默认样式属于组件包，宿主不强行覆盖内部背景和文字。不新增通用主题编辑器。

侧边面板采用用户指定的半透明磨砂背景，贴边占满当前显示器可用工作区高度，避开任务栏。宽度保存为工作区宽度的比例，显示器或缩放变化后重新计算；初始草图以 40% 展示并提供 20%～80% 调节，这些数值是设计默认，不是用户指定限制。实际宽度需满足组件最小可用尺寸且不超过工作区，达到边界时显示当前有效比例；内容过多时滚动面板画布；0.5.0去掉品牌标题和底部常驻设置，使用顶部紧凑图标，宽度等偏好按需打开。组件共用桌面外壳，自由拖动和缩放，面板逻辑布局单独持久化，不覆盖桌面几何。按用户 2026-11-13 补充确认，宽度比例和背景遮罩均须提供设置并持久保存，重建及下次启动恢复；透明度只作用于面板背景，不使文字及卡片整体变淡。两者属于宿主面板偏好，不写入组件业务配置，也不扩展为全局主题编辑器。0.4.0 将两项作为同一面板偏好保存在正常存储接口，开发验证只写隔离库。

草图中的背景模糊不作为真实桌面窗口磨砂的实测证据；系统级半透明与磨砂、缩放和重建后的效果需要加入桌面专项。若平台无法满足，明确报告限制和替代效果，不静默改成纯色后宣称完成。

行情主视图保留列表、来源、Last/Mark 身份、连接与时效状态及规则/历史入口；搜索合约、自选管理、规则编辑和历史按需进入详情。继续支持至少 20 个自选，主组件内部可滚动，不为每个标的自动创建窗口；精确价格判断、规则及通知语义保持不变。不在本轮增加图表、RSS 或监控业务。

### 3.4 现有实现的最小改造边界

| 位置 | 改造前基线 | 本次改造职责 |
|---|---|---|
| src/App.tsx、src/style.css | 管理侧栏和工作台展示混在同一主页面，浮窗带品牌栏 | 分离管理、辅助面板、独立组件容器和按需详情；移除常驻工作台展示主路径 |
| src-tauri/src/windows.rs、src-tauri/src/lib.rs | show/toggle 围绕 main 与浮窗，关闭浮窗会归位 | 统一处理第 3.1 节的场景、无焦点恢复、桌面层级、移动失败恢复与组件隐藏 |
| src-tauri/src/store.rs、src-tauri/src/widgets.rs | 数据版本 3；floating 同时用于布局及主会话归属校验 | 新增展示归属、实例显隐、层级及恢复偏好；迁移、会话所有权与原配置一致保存 |
| src-tauri/capabilities/host.json、src/WidgetFrame.tsx | 窗口白名单为 main、float-*、edge；组件按主窗口身份校验，展示轮询为 250 ms | 精确登记 panel 与详情宿主，区分主展示/详情角色；管理界面不获任意实例展示权限；隐藏释放现有轮询而非重建行情后台 |
| examples/market/ | 默认 760×720，行情、规则、历史集中在一个页面 | 同一组件包中分出紧凑展示与按需详情入口，保留原组件 ID、配置、自选及业务接口 |
| scripts/、SDK 与相关检查 | 原验收面向工作台和浮窗 | 只调整受影响契约、夹具与桌面专项；后台逻辑回归继续复用，不无差别重跑所有历史实机项目 |

本表保留改造前后职责；逐项实施与验证见11。优先复用现有窗口标签及受限资源协议；需要新增窗口标签时同步能力白名单和 Rust 会话校验，不能只放宽为任意窗口。组件资源、会话身份和详情角色由核心登记，组件页面不能自行声称归属。

### 3.5 数据迁移与兼容建议

- 在数据库版本3基础上实施v4事务迁移，沿用迁移前一致备份与完整性检查；本次不触碰真实数据库。
- 现有实例、包版本、配置、自选、存储及警报保留。旧 floating 不继续充当新展示模型的唯一标识：旧嵌入与浮窗实例初次迁移均归桌面，面板由用户后续移入；已有浮窗几何及置顶偏好可复用，嵌入实例按保存顺序安排可达初始位置，管理窗口几何不当作组件坐标。
- 旧版没有每实例显示状态时，首次迁移将旧实例设为可见桌面组件，不弹管理窗口、不激活前台；后续按新保存状态恢复。这是本次采用的迁移约定，不声称保留了旧版不存在的显隐数据。
- 显式保存的尺寸继续保留；仅无实例尺寸的行情组件采用新包的紧凑默认尺寸。真实最小尺寸依旧来自对应组件版本，不强迫未升级的旧包装进更小容器。
- 普通组件包及宿主接口主版本优先保持兼容；新详情入口作为可选能力，不要求旧时钟/卡片包跟随升级。旧行情包仍可显示其原页面，升级到新包后才提供紧凑主视图。
- 展示归属切换或持久化失败时，原实例仍可恢复，不提示保存成功；规则、连接和去重状态不随界面迁移重建。旧程序回退使用匹配数据备份，不强行降级打开新库。

### 3.6 资料边界与桌面专项门槛

已核对锁定版本 Tauri 2.12.5 的本机源码：WebviewWindowBuilder 提供 decorations、skip_taskbar、always_on_bottom、parent_raw，WebviewWindow 提供 hwnd；focused(false) 描述的是初次焦点。Windows 上 parent() 设置的是 owner，parent_raw() 的文档描述 WS_CHILD，二者不能混为桌面附着完成。源码位置及官方依据见 03 第 9.4 节。

候选方案是每个桌面实例使用独立承载窗口，面板集中承载其所属实例；Windows 桌面附着封装在平台模块。桌面宿主句柄的查找和恢复策略仍是专项调查项，不预先承诺某个桌面类名或消息在所有 Windows 上稳定，也不把“始终底层”当作桌面图标层之上的保证。

获准代码阶段后，先在隔离数据下验证时钟和卡片两个普通组件，按最小闭环记录：

1. 桌面层、Win+D 往返、普通应用遮挡及置顶切换符合第 3.1 节；任务栏与 Alt+Tab 不出现独立组件。
2. 背景展示不夺焦点，显式点击和设置输入可用；组件外区域、桌面图标和任务栏可正常操作。
3. 拖动、调整尺寸、当前可用缩放、重启和桌面宿主重建后位置可达；缺少的设备场景单列。未经授权不主动重启 Explorer，相关重建检查先由可控夹具验证，实际 Explorer 重启另行安排。
4. 关闭管理界面、收起面板、隐藏/恢复组件、在桌面与面板切换均符合唯一主展示会话；坏包及失败移动不破坏原实例。
5. 隐藏后展示轮询和临时会话归零；恢复不增加等价行情连接或规则；记录可见、面板收起和全部隐藏的资源，不能拿零视图低占用代替常驻展示成本。

专项若无法达到桌面层级、焦点或缩放的关键目标，记录最小复现和替代代价，停止扩大界面改造，不以普通浮窗替代后宣称完成。当前仅查资料与源码，尚无该专项的实机通过证据。

## 4. 组件包、加载与宿主接口

### 4.1 包格式基线

首版使用本地 zip 包，根目录为 manifest.json，页面资源位于 dist/。包内不携带 Node.js 后台、Rust 动态库或任意系统脚本。

按2026-11-13用户要求，当前源码将已有行情、时钟和卡片资源编译为预置组件，组件库合并预置目录与已登记包，不修改数据库结构或增加组件能力。只有首次添加未登记的预置组件时，才在内存生成相同包结构，并复用校验、隐藏试加载和事务启用；已登记包优先，不自动升级或降级用户版本。取消登记后预置入口仍保留，外部ZIP导入与独立构建继续支持。正式桌面首次添加和外部包试加载按11记录，历史安装包不因此视为已包含预置资源。

```json
{
  "schemaVersion": 1,
  "id": "local.example.clock",
  "name": "示例时钟",
  "version": "0.1.0",
  "hostApiMajor": 1,
  "entry": "dist/index.html",
  "defaultSize": { "width": 320, "height": 200 },
  "minSize": { "width": 240, "height": 120 },
  "capabilities": ["storage.instance"],
  "settingsSchema": {
    "type": "object",
    "properties": {
      "showSeconds": { "type": "boolean", "default": false }
    },
    "additionalProperties": false
  }
}
```

尺寸为逻辑像素。配置结构采用 [JSON Schema 2020-12](https://json-schema.org/draft/2020-12)的受支持子集，并在 SDK 中公布；默认值由宿主显式生成，不能假定验证器会自动写入。

稳定 ID、版本和实例 ID 分离。hostApiMajor 不匹配、未知必需能力、无效配置或缺少入口均拒绝启用，并保留原组件。ID、相对路径及保留名称的校验由宿主执行。

G1 实现补充：新包可声明 `loadCheck: 1`，在界面初始化完成后通过 SDK 的 `host.ready()` 报告就绪；这是接口 v1 的新增可选握手，未声明字段的 G0 草案包保留旧判定。当前受限试加载等待 10 秒内就绪及随后至少 800 ms 无捕获到的初始化错误，分别使用默认配置和旧实例配置/存储副本；失败不切换真实登记。时间上限是项目约定，不能证明未来任意时刻都不会出现组件错误。具体限制及静态资源类型见 [SDK 说明](../sdk/README.md)。

起步包限制为压缩包 20 MiB、展开后 50 MiB、最多 256 个文件项；这是本项目防止误导入的初始限制，不是性能实测值。拒绝绝对路径、越界路径、符号链接和重复覆盖入口。

### 4.2 加载策略与来源边界

1. Rust 资源解析器只读取已登记的组件版本目录，检查归一化路径、文件大小和类型，防止资源访问逸出包目录。
2. 现有工作台与浮窗使用独立于宿主页来源的组件 iframe。纠偏后复用同一包与消息契约，桌面组件及辅助面板的具体承载方式经专项决定；不把现有加载成功当作桌面展示已完成。组件不作为任意 React 源文件动态导入宿主构建。
3. 首选 Tauri 自定义资源协议；开发和 Windows 生产包的实际 URL/来源可能不同，由资源解析器返回并实测，不能硬编码为某个假定的 https 域名。
4. 组件页面采用允许脚本与自身来源的受控容器，限制顶层导航、弹窗及资源加载；宿主和组件的内容安全策略分别配置。不依赖 iframe 的 localStorage 保存实例业务配置。
5. 初始消息握手同时检查实际来源、发送窗口和对应 iframe；之后绑定实例会话和消息通道。目标来源精确匹配，不用通配符发送有权限的消息。依据：[网页消息标准](https://html.spec.whatwg.org/multipage/web-messaging.html)。
6. Tauri 权限是窗口/网页视图层面的机制，组件能力声明不自动成为权限隔离。Rust 网关必须自行校验能力和实例；不向组件提供通用 shell、任意文件系统或任意宿主命令入口。
7. G0 验证自定义协议、内容安全策略、消息桥、模块脚本和实际来源行为后，固定一种加载机制。若 iframe 路线不能满足核心目标，再评估单一独立网页视图容器并记录资源成本。

本方案面向可信本地组件，不宣称 iframe 或 React 错误边界能隔离所有恶意行为、死循环或网页进程崩溃。普通错误提供组件级提示；网页进程故障时应能重建视图，后台保持运行。

### 4.3 宿主接口 v1

采用“组件页面 → 宿主容器 → Rust 网关”，组件不直接维护币安连接。消息至少包括协议版本、请求 ID、会话、方法和参数；响应为结果或结构化错误，事件包含订阅 ID 与递增序号。

| 接口 | 语义与约束 |
|---|---|
| settings.get / settings.update | 仅当前实例；校验配置结构；成功响应表示已保存，失败保持旧值 |
| storage.get / storage.set | 当前实例命名空间；JSON 数据有大小限制，不接受调用者任意指定 instanceId |
| market.subscribe | 完整市场键；返回 subscriptionId 和当前带质量状态的快照；后续接收事件 |
| market.unsubscribe | 只释放当前会话拥有的订阅；重复释放幂等，不能影响其他消费者 |
| alerts.list / save / pause / remove | 仅授予警报管理能力；规则是宿主对象，编辑使用 revision 防止旧视图覆盖新状态 |
| history.list / notifications.test | 分页读取历史；测试使用明确测试事件，不修改真实规则状态 |

未知方法和能力默认拒绝；错误至少区分参数无效、能力不足、会话失效、版本不兼容、数据不可用、保存失败及超时。请求默认超时 10 秒；后台安装等较长任务以任务状态返回，不延长普通请求到无限等待。

会话在重新加载、移动到其他容器或包升级时失效；旧会话响应和取消请求不能作用于新会话。订阅增加采用消费者集合，不能仅按币种删除全部监听。

HTTP、RSS 和监控接口随 G4 实际组件增加；不为未知数据源预先建立完整通用后台。

### 4.4 安装、升级与回退

流程为：暂存包 → 校验和兼容检查 → 写入不可变版本目录 → 受限试加载 → 事务切换启用版本与实例配置 → 重建受影响视图。

- 试加载不授予写真实警报或发真实通知的能力。
- 不先删除旧版本。切换前保留实例配置快照；加载失败回到旧版本和相应配置。
- 配置增加可兼容的默认项；新结构无法读取旧配置时停止自动升级，保留旧版并提供清楚原因，不能静默重置设置。
- 失效会话及监听先回收，再接入新版本；共享行情和警报服务不随界面包重启。
- 卸载首先停用注册与实例引用；首版不附带自动批量清理历史版本目录的任务。

## 5. 行情与网络设计

### 5.1 数据身份与数据流

行情键统一包含交易所、市场、合约代码及价格类型。价格和阈值使用精确十进制字符串传输，Rust 使用精确十进制数比较；不先转为 JavaScript 浮点数或显示精度。

| 目的 | 数据源与处理 |
|---|---|
| 合约目录 | exchangeInfo 动态发现；quoteAsset 为 USDT，contractType 为 PERPETUAL 或 TRADIFI_PERPETUAL，status 为 TRADING；保留 tickSize、类型和交易状态，不用价格小数位推断 tickSize |
| Last 警报 | aggTrade 作为成交观测流；保留聚合成交标识和交易时间；按交易所发布粒度声明可观测范围 |
| Mark 警报 | markPrice 的选定更新频率；不用成交价替代标记价格 |
| 24 小时展示统计 | ticker；在 Mark 展示模式下仍标明该统计的 Last 口径 |
| 图表 | 后续按需接入 K 线，不默认持续渲染所有图表 |

官方当前说明 aggTrade 为按相同成交价和方向聚合的数据；Mark 有不同推送频率。最终端点、频率和限制以选定版本的[币安官方行情流文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/ws-streams/market)和实测记录为准，不能承诺观察到交易所未发布的所有瞬时轨迹。

订阅集合为：启用实例的持久自选、有效规则和临时视图消费者所需键的并集。视图隐藏不移除持久自选或规则消费者；移除最后一个业务消费者才可释放对应源订阅。不同实例的自选顺序和列表独立保存，数据源连接复用。

### 5.2 质量、时间与恢复

每条观测保留来源、价格类型、交易所事件/交易时间、本机单调接收时间、连接代次及源标识。必须区分：

- 连接状态：连接中、正常、重连中、离线。
- 流状态：有效、等待新数据、失效。
- 交易状态：可交易、暂停、下架/不支持，以及单独的标的市场时段。
- Last 最近成交时间与消息接收时间，不能只看 ticker 外层时间就把旧成交显示为刚成交。

Mark 选用 1 秒流时，初始失效检测上限设为连续 10 秒无有效更新；这是本项目可调参数，须覆盖实际抖动测试。Last 无新成交不单独判定连接故障；使用连接健康、合约状态和最近成交标记，只有新鲜有效成交观测才能驱动新的 Last 到价判断。

校验价格为正、标的和类型匹配、时间合理；拒绝非有限、负数和无效精度。对有源事件 ID 的流去重；对旧时间或旧连接代次消息丢弃并记录。没有事件序号时不假定时间戳永远是唯一标识。

若官方合并流携带市场类型字段，按其定义校验 USD-M 身份；不能只凭连接域名把其他市场帧归入当前规则。目录字段未知或发生协议变化时停止受影响订阅并给出诊断，不猜测类型。

断线或切换代理时增加连接代次，取消旧读写、订阅和退避任务；旧代次迟到消息不得污染新状态。恢复先等待各必要流的新鲜有效数据，再执行第 6 节恢复规则。缓存只用于显示“上次报价”，不能武装警报。

行情队列有界。队列满、解析持续失败等问题不能静默丢掉警报事件，应标为数据中断，进入受控恢复并记录原因。界面更新单独节流，初始上限每秒 4 次。

TradFi 的标的市场休市不直接等于合约停盘；按实际合约状态和各价格流判断，时段接口只作为相应标的市场信息。

### 5.3 网络控制

- 显式支持直连、手动 HTTP 和 SOCKS5；系统静态代理经解析后进入同一配置模型。PAC/WPAD 等未验证模式明确提示采用已支持的手动方式。
- REST 与 WS 使用一致的代理意图、超时及取消机制；代理凭证不进入日志、组件包或普通配置导出。
- 重连采用 1、2、4、8、16、30 秒上限的退避并加入抖动；识别到网络恢复/唤醒时立即安排一次受控重连，避免多个事件同时启动连接。
- 心跳、连接寿命和订阅限制按官方协议配置；G0 记录所用值和依据，不套用币安现货或其他交易所参数。
- REST 可在界面明确标识后提供显示回退；首版不以 REST 抽样或其他交易所价格代替规则选定的数据流。
- 代理修改先校验参数，再切换连接；失败保留用户设置及诊断，不修改系统全局代理。

## 6. 警报状态、去重与恢复

### 6.1 规则和运行状态

规则字段至少包含：id、revision、完整市场键、方向、threshold、模式 once/repeat、冷却秒数、启用状态、通知策略。触发频率与条件分离，保持用户已确认的行为；不额外引入指标或画线预警。

运行状态包括：是否已初始化、是否已返回等待侧、冷却截止、冷却内待补提醒、上次触发序号和单次完成状态。规则运行状态与事件由核心进程独占更新，视图只能通过显式命令修改。

专业产品的术语依据见 [TradingView 价格条件](https://www.tradingview.com/support/solutions/43000763313-how-to-use-price-alerts/)、[触发频率](https://www.tradingview.com/support/solutions/43000474415-differences-between-alert-frequencies/)及 [AICoin 官方使用说明](https://www.aicoin.com/zh-Hans/article/555351)。这些资料区分条件和频率；本节是结合用户明确答复制定的本地实现，不宣称软件间所有边界相同。

### 6.2 判断规则

向上“满足”为 price >= threshold，“等待侧”为 price < threshold；向下对称。价格字段按选定 Last/Mark 比较。

| 当前状态/输入 | 状态转移与事件 |
|---|---|
| 新建或重新开启，第一笔有效价满足 | 触发 initial_met；单次完成或重复进入冷却；设置界面先提示当前已满足 |
| 等待侧后第一次满足，且不在冷却 | 触发 reached；记录未返回等待侧 |
| 一直满足，未返回等待侧 | 不重复 |
| 冷却内返回等待侧 | 记录已重新准备；没有新提醒 |
| 冷却内重新满足 | 标记 pending；多个来回仅保留一个待补提醒 |
| 冷却到期，pending 且最新有效价满足 | 触发 cooldown_due 一次，清除 pending，重新开始冷却 |
| 冷却到期，pending 但价格不满足 | 清除 pending，等待下一次到价 |
| 冷却到期，无 pending | 不因一直满足而补发；等待新的到价过程 |
| 到期时数据无效 | 不递送；保留需复核状态，等待恢复后新价检查 |
| 暂停、删除或业务字段修改 | 取消原版本待补提醒与计时；修改阈值/方向/价格类型以新 revision 初始化 |

运行时冷却使用单调时间；持久化保存 UTC 时间与必要状态以支持重启恢复。检测到明显时钟跳变时重新校验时间状态并记录，不能以负间隔造成循环触发；具体容差随时钟测试确定。

冷却到期先进入待复核状态，再由到期后第一笔新鲜有效观测完成补提醒判断。尤其是 Last 长时间没有新成交时，不能拿很久以前的成交价格当作到期后的新证据；这会推迟至下一笔有效数据，而不是误判为网络断开。

### 6.3 恢复检查

- 每个有效流的新鲜数据独立恢复；不能因为 BTC 收到消息就使 ETH 规则恢复。
- 尚未处理、处于等待侧的规则恢复后若已满足，可触发 recovered_met 一次；记录实际新报价和接收时间。
- 冷却和 pending 状态保留并结合新价处理；如恢复前冷却尚未结束，不绕过冷却。
- 已触发单次规则维持完成；重复规则若先前已处理且未观测到返回等待侧，不因重连再发同一事件。
- 对恢复时有效的 pending，满足且冷却已结束时只生成一个事件，不能同时生成 recovered_met 和 cooldown_due。
- 不还原断档期间的首次穿越、次数或高低点，不将断档前后两价拼成已连续观测的轨迹。
- 暂停后开启视为新的显式监控动作，清除旧 pending；只改显示名称不重置规则业务状态。

### 6.4 自动化检查

使用固定时钟和固定输入序列覆盖 PRD 全部场景及下行对称情况，另覆盖：首次已满足、精确相等、小数边界、重复源事件、旧连接消息、持续满足、冷却内多次震荡、到期失效、规则暂停/修改、重启恢复和写入失败。

断网/恢复原因要有独立断言，不能只检查“有通知”。历史事件数量、触发序号和规则完成状态必须同时正确。

## 7. 持久化、通知与诊断

### 7.1 数据组织

SQLite 表按阶段引入，不一次创建未来组件的数据结构：

数据根目录位于 Windows 用户本地应用数据目录下的固定应用目录，与安装目录分离。相对布局为 workbench.sqlite、widgets/<id>/<version>/、backups/ 和 logs/；资源解析器只对已登记的组件版本开放页面文件。

| 数据 | 核心内容 |
|---|---|
| schema_migrations / app_settings | 数据版本、偏好、热键、窗口场景及网络配置的非敏感部分 |
| widget_packages / widget_instances | 活跃与前一包版本、实例设置、布局、启用状态和升级配置快照 |
| watchlist | 按实例保存标的与排序 |
| alert_rules | 规则、revision、冷却与去重的必要运行状态 |
| alert_events | 不可重复的逻辑事件及通知递送状态，同时承担小型待发送队列 |

规则事件采用唯一约束，例如 ruleId + revision + triggerSequence；序号由持久状态递增。规则状态变化和新增事件在同一事务提交。提交失败不报告保存成功，也不先发出一个没有持久记录的真实通知。

已保存的数据损坏时保留原文件和诊断，进入可恢复状态；不能无提示重建空数据库后继续报“正常”。

### 7.2 通知递送的实际边界

提交后再递送通知和声音，分别记录结果。静音只改变递送，历史仍保存。关闭系统通知仍可播放已开启的独立声音，不能复制参考代码中“关闭通知即关闭声音”的耦合。

事件递送状态区分 pending、sending、sent、failed、unknown、expired、suppressed。显式失败可有限重试；进程在 sending 时中断，重启后记为 unknown，不自动盲目重播。尚未尝试的事件恢复后检查时效，超过初始 2 分钟保留历史并标为 expired，避免开机堆积陈旧通知。

这是对本地系统通知无法与 SQLite 同一事务提交的处理约定：保证逻辑事件不重复保存，不承诺用户侧弹窗物理“恰好一次”。历史明确显示失败或不确定结果，并支持用户主动重试；重试不创建新的价格事件。

通知优先使用 Tauri 官方能力；独立声音由平台适配器处理。G0 必须验证安装后程序的通知身份和声音/通知组合，不依赖 Android 通道参数推断 Windows 支持。参考：[官方通知文档](https://v2.tauri.app/plugin/notification/)。

### 7.3 备份、迁移与日志

- 迁移前通过 SQLite 备份接口生成一致快照并检查完整性，不能在数据库使用中只复制一个主文件。依据：[SQLite 备份](https://www.sqlite.org/backup.html)。
- 迁移按版本顺序、在可回滚的事务中执行；迁移失败不切换为正常运行。恢复备份必须在停写和关闭连接后进行，保留失败副本。
- 旧程序遇到更新的数据版本时停止写入并给出说明，不能强行降级打开。
- 保存配置使用事务；失败不更新“已保存”状态。组件启用指针和相应配置切换尽量在同一数据库事务中处理。
- 日志采用轮转，初始最多 5 份、每份 10 MiB；记录连接代次、订阅数、数据失效、恢复、规则版本及通知结果，不记录代理凭证。
- 诊断导出包含版本、环境、计数和脱敏错误；默认不打包全部组件代码或敏感设置。

[SQLite 事务语义](https://www.sqlite.org/lang_transaction.html)是原子保存的依据，迁移和异常恢复仍须通过本项目故障注入检查。
